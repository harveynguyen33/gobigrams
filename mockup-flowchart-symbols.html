SECTION 3 — the decision

Three colour directions

Same nine shapes in every panel, drawn with the app's real 9%-alpha fill and 1.5px coloured stroke, plus a small flowchart so you can see the whole-canvas effect rather than nine isolated tiles.

The evidence that matters here: there is no standard colour scheme, and this is verified rather than assumed. draw.io's flowchart stencil file contains zero fillColor / strokeColor entries — the whole library gets one default style. Mermaid has a single nodeBkg for every node. Miro has one global palette with no shape mapping. So shape type carries no colour meaning anywhere in the industry, and whatever we pick is ours. That is why Option B has to say so on screen.

Option A — One colour, like every major tool

Every flowchart shape renders in the same neutral; colour is per node, chosen by the user.

Costs: the palette's ten tiles become silhouettes only — no colour to scan, and a fresh board is monochrome until the user colours it. Buys: it is literally what draw.io and Mermaid do (draw.io ships ONE default style, fillColor=#ffffff;strokeColor=#000000, for the whole flowchart stencil; Mermaid has one nodeBkg for every node), so nothing here can be called unconventional, and an export to draw.io loses no meaning. Honest read: the most defensible option and the least expressive. The app keeps its 6 accent keys per node, so colour does not disappear — it just stops being automatic.

Costs: we keep asserting a mapping the standards do not have, and the key has a COLLISION — Terminal and Manual operation are both green, so green means two unrelated things (verified in src/presets.ts). Honest read: draw.io and Mermaid do NOT do this; Lucidchart prescribes meanings but tells you outright that ignoring them is fine. So the grouping is legitimate, the word "standard" is not — hence the label.

Option C — A principled minimal palette (3 hues + neutral)

A hue marks only a node the READER must act on: where the flow starts or ends, what it does, and where it branches. Everything else is neutral.

The rule: green = entry / exit · cyan = an action (Process, Predefined process, Preparation) · amber = a branch (Decision) · everything else = the one neutral. That is 3 hues + 1 neutral instead of 5 groups with a collision. Costs: Input / Output, Document, Manual operation and Delay lose their violet / green / amber, so EXISTING boards visibly recolour (a one-line migration decision, not free). Buys: a reader learns the key in one sentence, the collision disappears, and I/O stops competing for attention with the thing the flow actually does. Honest read: closer to what the majors do than B (fewer automatic meanings), still more than A. Rejected sub-variant: keeping violet for I/O only — that is Option B with four hues instead of five, so the collision survives for no extra clarity.

SECTION 4

The Document description — four registers

One factual error to fix: the symbol covers the input OR the output of a document, and the current string names only the output. All four below describe the same tile.

CURRENT
wavy base · output 18 chars

Geometry + a use-word, and the use-word is WRONG in one direction: the symbol covers the input OR the output of a document (Lucidchart: "represents the input or output of a document, specifically").

CORRECTED, SHORT
wavy base · in or out 21 chars

Same register, same shape word, factually complete, and 21 chars sits INSIDE today’s shape-hint range (10–23). The smallest honest edit.

PLAIN GLOSS
a document, in or out 21 chars drops the geometry cue

No geometry word. Reads as a sentence and cannot be misread, but it drops the one cue that makes the palette searchable by shape — every other tile in the panel leads with its geometry.

CORRECTED, LONG
wavy base · document in / out 29 chars

Keeps the noun as well as the geometry, at 29 chars — 8 past today’s longest shape hint. Shown for register, not recommended as the tile string.

SECTION 5

The Terminal's proportions

Drawn to scale at the app's measured height of 180px, so you can point at the one that reads right. The current one is first.

One geometric catch worth knowing before you pick: the frame is a 200×100 viewBox with preserveAspectRatio="none" and rx=49, so it is stretched to the node box. The end caps come out 49×W/200 wide by 49×H/100 tall — which means narrowing the box makes the caps MORE elliptical, not rounder, and a true semicircular end actually needs ratio 2.00 (W = 2H). So the width and the cap roundness pull in opposite directions; the candidates below are the honest trade.

What I would pick: 1.50 (270 × 180). It is a 34px / 11% shortening, it is the smallest change that clearly answers "too long horizontally", the caps stay close to round (0.750 of a true semicircle, against 0.844 today — both read as a stadium), and it stays well clear of the 200px resizer floor. If you want it squarer, 1.33 (240 × 180) is the next honest stop; 1.11 is the floor and probably too tight for the label "Start". Going wider toward draw.io's 2.00 buys truly round caps and a longer box — that is the opposite of your note, so it is listed only as the reference point.
