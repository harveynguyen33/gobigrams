```md
# canvas-editor

The main surface: a React Flow canvas where the user drops nodes (9 resizable shapes),
connects them with edges, bends edges, drags labels, and animates flow payloads along
connections. Selecting a node or edge opens the inspector panel on the right.

## Sub-features

- node palette: 9 shapes (service, database, queue, external, actor, storage, gateway, group, note), all resizable
- edge system: bend handles, draggable labels with anchor rebase, flow payload animation (dots/dash/pulse/icon/envelope)
- inspector panel: per-selection editors (text, colour, flow, cardinality)
- canvas navigation: Figma/Miro standard (wheel = pan, Ctrl/Cmd+wheel = zoom, left-drag = box-select)
- undo/redo that preserves the live selection

## How to get to it (user POV)

- Open the app (dev server or built dist). The canvas is the whole screen; drag a shape
  from the left palette onto the canvas to create a node.

## Driving it with harness

Preconditions: dev server running (`npm run dev`).

**Create + select a node.** Run a browser harness against the page; a node div with
`.react-flow__node` must exist and gain the `selected` class on click. The round harnesses
in `checks/` (38 files, `node <file>.mjs` from repo root) are the canonical drivers.

## Gotchas

- The harnesses assume the demo board state ("Kafka rebalance", 3 nodes / 2 edges) — tests
  that mutate the board must restore it byte-identical.
- `checks/*.mjs` use `DS_ROOT` to point at a tree; default is the repo dir.
```

```md
# boards

Named, persistent diagrams. The user saves the current canvas under a name, reopens it
later from the board dialog, and the app autosaves so a refresh never loses work.

## Sub-features

- save / save-as with a name; board list dialog with open + delete
- autosave on change (debounced) with reconnect on reload
- served by the dev-server API (`/api/boards`): atomic writes, one `.bak` generation

## How to get to it (user POV)

- Click the board name in the top bar — the dialog lists saved boards; pick one to load it.

## Driving it with harness

Preconditions: dev server running; a browser harness with localStorage access.

**Save + reload.** `checks/package-o-board-dialog.harness.mjs` drives the dialog end to
end: create a board, save, reload the page, assert the board reopens with the same graph.

## Gotchas

- Stale persisted UI state is CLEARED + re-initialised, never migrated (house rule).
- The demo board `boards/mu01q1ue3a854b81.json` must stay byte-identical — round harnesses
  restore it after mutating tests.
```

```md
# appearance

Five themes (dark, light, paper, midnight, contrast) plus OS-follow, picked from the
Appearance pane in Settings; every theme is token-driven (a pinned hex ceiling in
styles.css, enforced by the round harnesses). Node fills, edge strokes and label plates
can also carry authored colours, including two theme-invariant neutrals (black/white)
and a custom picker.

## Sub-features

- theme cards with mini-sidebar previews; System card previews the live OS theme
- token-only CSS: --surface/--accent/... consumed everywhere; 36px colour cells in a 6-column grid
- authored colours on nodes, edge strokes, table accents; custom colour via native input under a styled trigger
- no-flash boot: the theme script applies the saved theme before first paint

## How to get to it (user POV)

- Open Settings → Appearance; click a theme card to apply it straight away.

## Driving it with harness

Preconditions: dev server running.

**Theme + colour checks.** `checks/round-ag-colors.mjs`, `checks/round-ao-colour-and-nub.mjs`
and `checks/theme-boot-sync.mjs` assert the token values per theme, the boot sync, and the
colour-grid geometry.

## Gotchas

- Zero new hex in component CSS is a hard rule — the harness ratchet pins styles.css at 144.
- Theme previews must NOT follow the current pick: the System card previews the OS theme
  via matchMedia, the fixed cards preview their own tokens.
```
